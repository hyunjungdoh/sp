\section{Design of \sys}
\label{sec:design}

In this section, we describe how \sys assesses whether a vulnerability in an upstream library $U$ remains triggerable through a downstream library $D$.
Given closed LLVM bitcode for $D \cup U$, the exported interface $I$ of $D$, and a sink location $s$ in $U$, \sys synthesizes a client of $D$ and searches for an explicit input under which that client reaches $s$.
When no such client exists, it reports the unrealizable obligations that block synthesis.
The remainder of this section develops the three phases that address Challenges~1--3 from \autoref{sec:moti}.

\PP{Overview}
\autoref{fig:overview} summarizes the workflow.
In P1, \sys recovers witness sequences---call chains from an export in $I$ to a function containing $s$---by resolving indirect calls with a slot-sensitive call relation and retaining only paths whose formulas are satisfiable.
In P2, it projects each witness onto client obligations over entry-rooted cells, determines how those obligations can be realized through $D$'s interface, and produces either a configuration-complete call plan or a set of open obligations.
In P3, it searches for concrete inputs under that plan using distance-guided concolic execution.
Throughout, the three phases share the same resolved call relation, so planning and exploration do not invent callees that sequence recovery has already ruled out.

As a running example, we reuse the libtiff--libjpeg-turbo case from \autoref{sec:moti}, where strip decoding enters through \texttt{TIFFReadEncodedStrip} and the sink lies under JPEG decompression.

\subsection{Recovering Call Sequences with Slots (P1)}
\label{subsec:p1}

P1 recovers the call sequences through which a client of $D$ can reach $s$ under conditions that can install the vulnerability's trigger.
At the $D$--$U$ boundary, the decisive transfers are often indirect: callback fields, registry-selected handlers, and C++ virtual calls.
Following only direct edges therefore misses sequences that arise in practice, whereas treating every signature-compatible function as a callee invents sequences that no client can install.
P1 accordingly resolves each indirect call not merely by type, but by the dispatch slot from which the callee is read.

\subsubsection{Slot-Sensitive Call Relation}
\label{subsubsec:slots}

\sys first constructs a call relation over all defined functions of $D \cup U$.
Direct calls contribute a single edge.
For an indirect call $c$, it computes two target sets.
The signature layer $T_{\mathrm{sig}}(c)$ contains every address-taken function whose LLVM type matches $c$; under the C calling convention this set over-approximates every well-typed callee, and P3 later uses it for conservative unreachability proofs.
The slot layer $T_{\mathrm{slot}}(c)$ refines that set by a field- and object-sensitive flow of function constants in the style of multi-layer type analysis~\cite{lu2019where}.
Addresses are named either by source field paths derived from DWARF and LLVM struct layouts, or by abstract objects for allocas, globals, and opaque allocator results.
Stores and loads move function tokens through these locations; SSA operations (\texttt{phi}, \texttt{select}, casts, and GEPs) copy them; and calls transfer them among actuals, formals, and returns.
Virtual calls are handled by class-hierarchy analysis on the receiver's static class and stored vtables, rather than by merging the vptr into the object's data cell.
When dispatch is keyed by a symbolic name---as in codec registries---\sys also records the constant strings that select a handler.
The slot of $c$ is the cell or vtable entry that $c$ reads, and $T_{\mathrm{slot}}(c)$ retains only functions that can flow into that slot.
An empty slot set means no function constant reaches $c$; such calls are excluded from sequence search, so signature-compatible but never-installed callees do not appear as phantom edges.

\subsubsection{Witness Extraction}
\label{subsubsec:sequences}

Let $G$ be the graph whose edges are the direct callees together with every $t \in T_{\mathrm{slot}}(c)$.
\sys restricts $G$ to the cone of functions that can reach $s$ and then enumerates simple paths from interface starts in $I$, preferring fewer indirect edges and shorter length.
After accepting a path, it bans that path's final edge into the sink before searching again, so successive witnesses differ.

For a candidate sequence $\pi = f_0 \cdots f_n$, \sys does not retain the full CFG of each $f_i$.
Inside $f_i$ it first collects the \texttt{BasicBlock}s that can reach the call of $f_{i+1}$---or the sink instruction, when $f_i$ is last---by walking predecessors from those goals.
Within this slice it selects the shortest entry-to-goal path among blocks that still reach a goal, breaking ties by block name.
The conjunction of the branch conditions on that path, together with dispatch equalities that bind each indirect slot to the next function of $\pi$, forms the path formula $\varphi_\pi$.

\sys then solves $\varphi_\pi$ against the export cells of $f_0$.
The solver walks the sequence under a memory map from SSA values to cells, resolves local allocas through their reaching stores, and folds summarizable callees---functions whose stores into the export object occur only at constant offsets---so that residual analysis begins at the first step that cannot be folded.
Only sequences for which this solve succeeds are emitted as witnesses; graph-reachable but value-infeasible candidates are discarded.

In the libtiff example, one retained witness begins at \texttt{TIFFReadEncodedStrip}, crosses into JPEG decoding, and records the decode slots that must already hold the JPEG handlers.
Those slots, rather than a call to \texttt{jpeg\_skip\_scanlines}, are what a downstream client must establish.

\PP{Output of P1}
P1 yields the set of satisfiable witnesses and the shared map $T_{\mathrm{slot}}$, which is serialized for the executor.
P2 consumes the witnesses; P3 reuses $T_{\mathrm{slot}}$ when ranking states by sink distance.

\subsection{Recovering Arguments and State with Cells (P2)}
\label{subsec:p2}

Even a satisfiable witness does not yet say what a client of $D$ must supply.
Its formula constrains many locations that $U$ allocates and initializes only after control crosses from $D$ into $U$, and treating those locations as client duties either over-constrains the harness or obscures why synthesis fails.
P2 therefore projects each witness onto obligations that are visible at $D$'s interface, and plans interface calls that realize them.

\subsubsection{Cells and Alias Identity}
\label{subsubsec:cells}

\sys represents each obligation site as a \emph{cell}: the alias class of memory locations named by an access path rooted at an argument of the witness entry $f_0$ (or at a global when required).
The path suffix is a sequence of source struct types and constant byte offsets.
Two IR pointers denote the same cell when the location analysis maps them to the same path.
Accesses through a variable struct-field index are rejected, because they do not name a unique cell; variable array indices collapse to a single element cell.
Cells thus give each obligation a stable, client-visible identity instead of an ephemeral SSA value.

\subsubsection{Boundary Projection}
\label{subsubsec:projection}

Along a witness $\pi$, a crossing edge is a call from a function defined in $D$ into one defined in $U$.
The crossing roots are the cells of the pointer actuals at those calls, when those actuals are expressible from $f_0$.
A constrained cell of $\varphi_\pi$ is a boundary cell if it lies inside some crossing root---that is, if it shares the root and has a suffix for which the crossing actual is a prefix.
A prefix cell is a constrained cell of a client-owned object argument that the $D$ prefix must satisfy in order to reach the crossing.
Client obligations comprise the boundary cells, the prefix cells, and the own cells of $\varphi_\pi$; cells that $U$ writes only after crossing are dropped.
Structural obligations, such as a cell that carries a file name, are retained even when no concrete value has been fixed.

\subsubsection{Realizability by Taint and Writers}
\label{subsubsec:realize}

For every defined function, \sys records the fields it stores and loads, as well as its control references---the fields read by branch and \texttt{switch} conditions, recovered by a backward SSA slice of the condition in which a field load ends the slice and an \texttt{alloca} load continues through the stores into that slot.

Given a cell $c$, the writers of $c$ are the callable exports of $D$ whose inner closures---calls that do not re-enter another callable export---contain a store that can satisfy $c$'s constraint.
Whether a writer carries $c$ is decided by interprocedural taint from its formals along SSA edges, local store/reload pairs, loads through derived pointers, and call/return summaries.
Only writers that carry $c$ are admitted for boundary and prefix cells.
When the entry fills $c$ solely by copying from a source field, the obligation is rewritten onto the setters of that source.
Opaque held objects may be realized through constructor levers: integer formals of producers that taint-reach the constrained field.
Cells written under a tag selected by a constant key from P1 are realized by the corresponding key setters.
Finally, if the entry or a producer it expands reads input while writing $c$ with a non-constant, $c$ may be treated as a file-content lever.

\subsubsection{Plan Synthesis}
\label{subsubsec:plan}

Each obligation is assigned the first matching realization among own writes into public fields, producer levers, key setters, interface writers, library-determined construction, file-derived writes, and---when none apply---an open residual.
Write obligations are covered by a greedy set cover of at most $K$ writers, matching the harness grammar that offers $K$ writer choices before the entry; uncovered write cells remain open.
The resulting plan unions, over witnesses, the chosen entries, guards, levers, keyed setters, and writers, together with an AND--OR grammar over producers of held handle types, ordered by production cost.
Indirect edges of a passing witness must likewise be realized---by a registry key with file input, by an installer reached while reading input, or by a planned writer or key setter---or they are reported open.

In the libtiff witness, projection retains the strip-buffer cell of \texttt{TIFFReadEncodedStrip} and the decode-state cells that cross into JPEGDecode, while discarding libjpeg-internal upsampler fields initialized after the crossing.
A \texttt{NULL} strip buffer then appears as an argument obligation of the plan: the trigger lever discussed in \autoref{sec:moti}, rather than a claim about how typical TIFF clients behave.

\PP{Output of P2}
When every obligation of some witness is realized, P2 emits a configuration-complete harness plan whose remaining unknowns are explicit inputs for P3.
When a required cell or dispatch edge remains open, it reports a configuration failure, distinct from a later failure to find an input.

\subsection{Searching Explicit Inputs with Concolic Execution (P3)}
\label{subsec:p3}

Once the plan has no open obligations, the remaining task is to search the harness input domain---files, byte buffers, and related scalars---for an input that drives execution to $s$.
Full symbolic execution tends to exhaust its budget in the solver before leaving parser prefixes.
\sys therefore runs a generational concolic search in which a concrete seed decides branches, addresses, and allocation sizes without invoking the solver, and untaken sides become pending flips that are solved only when selected.
States are ranked by a sink distance computed on the same $T_{\mathrm{slot}}$ relation as P1, so signature-only phantom callees do not steer exploration; unreachability claims, conversely, rely only on the coarser $T_{\mathrm{sig}}$ layer.
We defer the remaining search machinery and its evaluation to \autoref{sec:eval}.
