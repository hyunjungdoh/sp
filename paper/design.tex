
\section{Design of \sys}

We present the design of \sys, which assesses the exploitability of propagated vulnerabilities by recovering the required downstream configuration context and identifying inputs that trigger vulnerabilities under that context.

Before describing the analysis procedure, we define its inputs and vulnerability target.
%
Given an upstream component, a downstream application, and an upstream PoC input $X$, \sys analyzes a vulnerable function $f_v$, manually identified by reproducing the PoC on the upstream component.
%
If the fault occurs at a function call (\eg, \texttt{memmove()} in \autoref{lst:moti_vul}), the called function is selected as $f_v$; otherwise, the function containing the faulting instruction is selected.
%Given an upstream PoC input $X$, \sys targets a vulnerable function $f_v$, manually identified by reproducing the PoC on the upstream component.
%
%If the fault occurs at a function call (\eg, \texttt{memmove()} in \autoref{lst:moti_vul}), the called function is selected as $f_v$; otherwise, the function containing the faulting instruction is selected.

\PP{Overview}
\autoref{fig:overview} illustrates the workflow of \sys.
%
In P1, \sys recovers configuration contexts required to reach the vulnerable function $f_v$ from downstream public APIs.
%
Because identifying trigger paths alone does not reveal how their conditions can be established, \sys performs \textit{setup attribution} to connect path conditions with the public APIs that can satisfy them.
%
In P2, \sys generates executable harnesses from the recovered configuration contexts.
However, the identified setup APIs alone may not be sufficient to reproduce the intended execution. Therefore, \sys employs \textit{directed harness synthesis} to construct API call sequences and incorporate additional configuration choices that guide execution toward the vulnerable function.
%
In P3, \sys analyzes whether the generated harnesses can trigger the vulnerability through the downstream application.
To distinguish vulnerability triggering from mere reachability, \sys employs \textit{concolic execution} to explore configuration choices and validate exploitability.

\PP{Design assumptions}
\sys assumes that the upstream and downstream components are available as LLVM intermediate representation (IR) with debug information, which provides function signatures, structure layouts, and field information needed for cross-boundary analysis.
%
We assume the downstream application is accessed through its public APIs.
Accordingly, \sys recovers configuration contexts that can be established through these APIs, without directly modifying the application's private internal state.

\subsection{Configuration Context Recovery (P1)}\label{subsec:p1}
P1 recovers the configuration context required to trigger an upstream vulnerability through a downstream application. \sys first constructs a cross-boundary call graph and identifies trigger paths from downstream public APIs to the vulnerable operation. It then analyzes the conditions along these paths and identifies the public APIs that can establish the required memory state.

\subsubsection{Call Graph and Entry Points}
Constructing a cross-boundary call graph requires resolving indirect calls through function pointers and virtual dispatch~\cite{li2025redefining, mlta-ccs19, liu2024improving}. For example, a downstream application may register a callback that the upstream component invokes later. 

To resolve indirect calls across both components, \sys performs a field-sensitive, flow-insensitive points-to analysis. The resulting call graph is represented as $G=(F,E)$, where $F$ denotes functions in both components and $E$ denotes their calling relationships.


%To resolve these calls, \sys performs a field-sensitive, flow-insensitive points-to analysis over both components. \sys connects function-pointer stores to indirect-call loads and resolves virtual calls through vtable entries. Together with direct calls, these relations form a call graph $G=(F,E)$, where $F$ represents functions in both components and $E$ represents their calling relationships.

Specifically, \sys constructs the call graph by adding three types of edges to $E$.

\begin{itemize}
    \setlength\itemsep{0.3em}
    \item For direct calls, it connects each caller to its explicitly named callee.
    
    \item For indirect calls, it uses points-to analysis to identify possible callees from function-pointer assignments and loads. For example, if a function pointer \texttt{ptr->field} stores the address of $f$ and an indirect call later loads this field, \sys adds an edge from the caller to $f$. 

    \item For virtual calls, it resolves possible targets through \texttt{vtable} entries, including overriding methods in derived classes.
\end{itemize}

\PP{Entry-relative path condition recovery}
For each trigger path $\pi$, \sys recovers the path conditions and expresses the associated memory locations using \textit{entry-relative cells}.
Each cell is defined as $c=(o,\alpha)$, where $o$ is an argument of the entry point $f_0$, and $\alpha$ is a sequence of fields accessed through $o$ (empty when no fields are accessed).

\PP{Setup API identification}
For each entry-relative cell,
\sys identifies public APIs that can establish a value satisfying its path conditions. It first locates \texttt{store} instructions targeting fields that match the final field of $\alpha$ in type and byte offset. Let $W(c)$ denote the set of functions containing these \texttt{store}s. \sys then traverses the call graph backward from $W(c)$ to identify public APIs that can reach these functions.

However, a matching \texttt{store} does not necessarily indicate a valid setup API. Therefore, \sys checks three requirements: \circled{1} the API modifies the object associated with the required cell, \circled{2} the stored value can satisfy the recovered path condition, and \circled{3} the API does not release the required object. For the second requirement, caller-controlled values are considered configurable, while constants violating the condition are rejected.

\doh{For \circled{1}, \sys compares the points-to targets of the \texttt{store} pointer and the API’s object parameter to determine whether they alias. If they do not, \sys rejects the candidate. For \circled{2}, \sys inspects the value written by the \texttt{store}. If that value is not a compile-time constant, \sys treats it as chosen by the caller and accepts it. If it is a constant, \sys accepts it only when the constant satisfies the path condition of $c$. For \circled{3}, \sys finds calls to \texttt{free}, \texttt{delete}, or other functions that end an object’s lifetime, and rejects the API when a pointer argument of such a call refers to the same object as the API’s object parameter.}

\PP{Precision of setup attribution}
The recovered configuration contexts are candidates rather than guarantees of executable trigger paths. The call graph and value analysis may over-approximate feasible behavior, and the selected setup APIs represent a bounded set of configuration alternatives. Therefore, P2 uses these contexts to generate executable harnesses, while P3 determines whether the upstream PoC input actually triggers the vulnerability under the established configuration.

\PP{Registration constant recovery}
Although the constructed API sequence establishes the required configuration, it may not select the intended indirect-call targets along the trigger path.
This is because selecting a registered function may depend on additional constants associated with its registration. For example, a library may register \texttt{decodeRAW()} with a key \texttt{2} through \texttt{registerDecoder(2, decodeRAW)} and later use that key to select the registered function. Even if P1 identifies \texttt{decodeRAW()} as an indirect-call target, the harness needs the corresponding key to invoke it at runtime.

To address this issue, \sys identifies registration-related constants for each indirect-call target $t$ along the trigger path.
Specifically, it examines constants stored alongside the address of $t$, passed with $t$ to registration functions, or used by factories that construct objects containing $t$.
When registration uses a constant table, \sys examines its individual entries.
%

The recovered constants are added as candidate values for the corresponding harness arguments, alongside an option to omit the associated setting when applicable.

\PP{Configuration dependency recovery}
The preceding steps construct an API sequence and recover values for indirect-call dispatch.
However, execution along the trigger path may also depend on configuration settings that P1 cannot express as entry-relative cells.
These settings may reside in objects created internally by the downstream application or originate from defaults used by the upstream library.

Because this object is not accessible through the entry-point arguments, P1 cannot recover the setting as an entry-relative cell.

To identify such settings, \sys traces backward from branch conditions and operands of vulnerable operations along the trigger path.
It follows values to their definitions and field reads to their corresponding writes, identifying configuration lookups and public setters that influence these values.

At the call site, the receiver is the object being queried, and \sys recovers the setting identifier from a constant string argument rather than by matching against a list of known names. It then finds a public setter on that object that writes the same memory the lookup reads.}
In the \texttt{OIIO} example, this analysis connects the internal \texttt{max\_raw\_memory\_mb} field to the client-configurable \texttt{raw:max\_raw\_memory\_mb} attribute.
To avoid unrelated dependencies, \sys restricts the analysis to functions reachable from the entry point and preserves calling contexts when traversing shared helpers.
For example, without caller-context information, a shared utility such as \texttt{std::min()} could incorrectly associate configuration values from unrelated callers with the trigger path.


\subsubsection{Output of P2}
P2 produces an executable harness from the recovered API sequence, registration constants, and configuration settings.
The harness initializes the required objects, invokes the setup APIs, and calls the downstream entry point with the upstream PoC input $X$.
%
For example, the harness for \autoref{lst:working_example} invokes \texttt{createContext()}, \texttt{setLimit(ctx, n)}, and \texttt{process(ctx)} in sequence, where \texttt{n} represents a configuration choice guided by the recovered path conditions.
%

For settings with default values, the harness considers both leaving the setting unset and invoking its setter with a non-default value.
In the \texttt{OIIO} example, \sys assigns higher priority to explicitly setting \texttt{raw:max\_raw\_memory\_mb} than to unrelated settings.
These alternatives are retained as configuration choices rather than mandatory constraints.
%

Using the call graph constructed in P1, \sys computes the shortest call-graph distance from each function to $f_v$.
Along with the generated harness, \sys passes these distances and the indirect-call targets recovered by P1 to P3.

\subsection{Exploitability Analysis (P3)}
Given the harness and configuration choices, \sys performs concolic execution to determine whether the upstream PoC input $X$ triggers the vulnerability through the downstream application~\cite{majumdar2007hybrid}.
The input $X$ remains fixed, while the configuration choices are explored to identify a triggering execution.
%

\sys builds its concolic executor on KLEE~\cite{cadar2008klee}.
Unlike standard KLEE, which explores every branch over symbolic inputs, \sys follows the execution path determined by the current concrete configuration rather than forking at every symbolic branch.
%
Branches depending only on $X$ follow its fixed values, while branches depending on configuration choices can be flipped and checked for satisfiability using an SMT solver~\cite{de2008z3}.
Satisfying assignments are used to generate new configurations. 
%for subsequent executions.

\PP{Seed scheduling}
Concolic execution starts from the configuration established by P2 and the given PoC input $X$.
\sys maintains a pool of execution states, each associated with a concrete assignment to the configuration choices.
%
To guide exploration toward $f_v$, \sys performs seed scheduling based on call-graph distances.
States closer to $f_v$ are explored first, while those with no call-graph path to $f_v$ are discarded.

When a branch depends on a configuration choice, \sys flips its condition and invokes the SMT solver to check whether the resulting path constraints are satisfiable.
Each satisfying assignment generates a new execution state with an updated configuration, which is added to the state pool for subsequent exploration.
The solver checks constraint satisfiability, while actual reachability and vulnerability triggering are verified through execution.

\sys also explores configuration alternatives retained by P2, including optional setup APIs and alternative configuration values.

\PP{Indirect-call handling}
Although P1 identifies possible indirect-call targets, the actual callee depends on the function pointer selected at runtime.
%

To establish the required dispatch state, \sys first executes the initialization sequence generated by P2 with a concrete dispatch key, before forking concolic execution states.
%
This initializes dynamically populated registries, such as plugin or codec catalogs, whose contents are then inherited by subsequent states.

During concolic execution, \sys follows the target indicated by the concrete function pointer rather than replacing it with a target recovered by P1.
It checks whether the observed target is included in the statically recovered call relation for that call site.
A mismatch is recorded as a warning but does not prevent the call.
The recovered targets also contribute to the call-graph distances used for seed scheduling.
Thus, static call relations guide exploration, while actual dispatch remains governed by the program's runtime state.


\PP{Engine support}
Executing the upstream and downstream components together requires support for their C/C++ runtime dependencies.
%
However, KLEE may terminate execution states when encountering unsupported \texttt{libstdc++} functionality or unmodeled external functions, such as \texttt{strdup()} and \texttt{getenv()}, preventing exploration from reaching $f_v$.
%
To address this limitation, we implement a custom \texttt{libstdc++} library and extend KLEE's symbolic environment models to support these runtime and external calls.
The extended models avoid introducing additional constraints that would incorrectly restrict feasible program behaviors.

\PP{Trigger criterion and termination}
\sys confirms a trigger by replaying the recovered configuration with the fixed PoC input $X$ and checking for the manifestation expected of that vulnerability. For memory-corruption bugs, this is an AddressSanitizer report of the same error class as the upstream PoC on an execution that reaches $f_v$. For denial-of-service bugs, where no memory error is expected, \sys instead treats a hang or abort that matches the upstream PoC's failure mode as the trigger. Reaching $f_v$ without that manifestation is treated as reachability, not as a trigger. Exploration ends when the analysis budget expires, when a solver or engine limit is hit, or when no further satisfiable configuration flips remain.
