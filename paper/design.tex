\section{Design of \sys}
\label{sec:design}

In this section, we describe the design of \sys, which assesses whether a vulnerability in an upstream library is exploitable through a downstream library.
\sys recovers the calls and runtime state needed to reach the vulnerable code, and then searches for inputs that trigger it.

\PP{Overview}
\autoref{fig:overview} shows the workflow of \sys, which comprises three phases.
In P1, \sys recovers trigger paths, i.e., call sequences from a public API of the downstream library $D$ to the vulnerable code in the upstream library $U$, together with the conditions those sequences require.
In P2, \sys generates a client harness that invokes the recovered API sequence and establishes the runtime state those conditions demand.
In P3, \sys performs concolic execution on the harness to find concrete inputs that trigger the vulnerability.

\subsection{Recovering Trigger Paths (P1)}
\label{subsec:p1}

P1 addresses C1 by recovering the configuration context of the sink $s$ across the $D$--$U$ boundary.
The context is a pair $(\pi,\varphi_\pi)$.
The \emph{trigger call path} $\pi=f_0\rightarrow\cdots\rightarrow f_n$ runs from a public API of $D$ to the function containing $s$ in $U$, and the condition $\varphi_\pi$ specifies when that path can execute under one shared entry state.
\sys recovers the path and the condition in turn, then keeps only paths whose indirect calls a real client of $D$ can set up.

\begin{enumerate}
    \item \textbf{Trigger call path.} $D$ often reaches $U$ through indirect calls (function pointers, callbacks, virtual calls), which a call graph of explicit callees cannot see.
    \sys therefore links each store of a function address to the indirect calls that later load it.
    It starts paths only from the outermost public APIs of $D$ that a client can actually invoke with arguments it can construct.
    \item \textbf{Feasibility.} Values and branch conditions along $\pi$ must hold jointly under that single entry state, and every indirect call on $\pi$ must be one the client can configure.
    \sys maps memory accesses back to locations derived from the entry arguments so one satisfiability check covers both modules, and it discards indirect call edges that no client API sequence can establish.
\end{enumerate}

\PP{Resolving Cross-Boundary Indirect Calls}
Consider a callback that $D$ registers by storing a function address in an object field.
$U$ later loads that address and calls through it, so the edge between the two modules never appears in a direct call graph.
\sys recovers such edges by linking each function-address store to the indirect calls that load the same location.

For this purpose, \sys runs a field-sensitive, flow-insensitive points-to analysis restricted to function pointers.
Let a location $\ell=(o,\alpha)$ be an object $o$ and a field $\alpha$ within it, so a store into one field is never confused with another.
Let $\mathcal{L}$ be the set of locations and $\mathcal{F}$ the set of functions in $D$ and $U$.
For each $\ell\in\mathcal{L}$, $\operatorname{Pt}(\ell)\subseteq\mathcal{F}$ is the set of functions whose addresses may be stored at $\ell$.
The analysis proceeds in three steps.
\begin{enumerate}
    \item For each store of a function address, add that function to $\operatorname{Pt}(\ell)$ of the target location.
    \item Propagate these sets along memory and pointer flows until a fixed point.
    \item Relate locations with compatible field paths, since the same storage can be accessed at different levels of an object.
\end{enumerate}

Using the result, \sys adds a call-graph edge from each indirect call that loads from $\ell$ to every type-compatible function in $\operatorname{Pt}(\ell)$.
An empty set yields no edge.
Virtual calls are resolved over the possible derived classes of the receiver.
These edges complete the call graph $G=(V,E)$ across the $D$--$U$ boundary.

\PP{Identifying Entry Points}
$G$ shows how $s$ can be reached, but not where a client can \emph{start}.
A valid start must satisfy two conditions.

\begin{enumerate}
    \item \textbf{Outermost among public APIs.}
    If a public function $f$ is called by another public function $c$ that also reaches $s$, starting at $f$ would skip $c$'s setup.
    Internal (non-exported) callers do not disqualify $f$: they are part of $D$'s implementation below the client API.
    \item \textbf{Constructible arguments.}
    Export and a header declaration are not enough.
    If any argument that the client must supply as an owned object or handle has a type the client cannot construct (e.g., an opaque handle with no public constructor), no well-formed client can call $f$, and projecting path conditions onto $f$'s arguments would be meaningless.
\end{enumerate}

Let $I$ be the public interface of $D$: symbols that $D$'s shared library exports and that $D$'s installed headers declare.
Let $I^{\star}\subseteq I$ be those functions for which every client-owned object or handle argument has a constructible type.
Let $R(s)=\{v\in V\mid v\leadsto s\}$ be the functions that can reach $s$ on $G$.
\sys selects entry points as
\[
B_{\mathrm{entry}} =
\left\{
f\in I^{\star}\cap R(s)
\;\middle|\;
\nexists c\in R(s)\cap I:(c\rightarrow f)\in E
\right\}.
\]
Each selected function is a root a client can actually call, and path conditions are stated over its arguments.
\sys enumerates candidate paths from these entry points to the function containing $s$.
A public symbol outside $I^{\star}$ may still appear later on a path as an internal step; it is never the first function of $\pi$.

\PP{Checking Path Feasibility}
A call-graph path alone does not tell whether a client can follow it.
\sys therefore separates \emph{value feasibility} from \emph{setup feasibility}.

\paragraph{Value feasibility.}
Under one entry state at $f_0\in B_{\mathrm{entry}}$, (i)~each call on $\pi$ must be reached through the appropriate branches, and (ii)~each indirect call must load the callee that $\pi$ designates.
\sys encodes both as a path condition
\[
\varphi_\pi =
\varphi_{\mathrm{control}}\land
\varphi_{\mathrm{dispatch}},
\]
where $\varphi_{\mathrm{control}}$ is the conjunction of those branch conditions and $\varphi_{\mathrm{dispatch}}$ constrains each indirect-call slot to the designated target.

To state $\varphi_\pi$ over the entry state, \sys works backward from the sink.
\begin{enumerate}
    \item Collect the requirements of each function and propagate them to its caller, so branch choices stay consistent with the state the caller passes.
    \item Represent each relevant memory access as a \emph{cell} $(i,\alpha)$: the $i$-th argument of $f_0$ together with a constant field path $\alpha$ from that argument.
    Accesses in callees are mapped back to these cells across calls, so deep conditions become conditions on values available at $f_0$.
    \item State the requirements of indirect calls over the same cells used to resolve their targets.
\end{enumerate}

\sys then checks satisfiability of $\varphi_\pi$ on those cells with a static constraint solver.
If $\varphi_\pi$ is unsatisfiable, the path is discarded.

\paragraph{Setup feasibility.}
Even when $\varphi_\pi$ is satisfiable, an indirect edge on $\pi$ is usable only if a real client of $D$ can \emph{install} the chosen callee before the call runs.
\sys treats an indirect edge as client-setuppable when at least one of the following holds (the same mechanisms P2 later uses in the harness):
\begin{enumerate}
    \item A \emph{name-based selector}: the client passes a constant string (format name, codec id, \ldots) that the library uses to choose the callee.
    \item An \emph{input-driven registration}: while $D$ reads the client's input, it runs a routine that stores the callee into the call slot.
    \item An \emph{explicit API write}: the client calls a public setter that stores the callee (or otherwise configures the slot).
\end{enumerate}
If $\varphi_\pi$ is satisfiable but some indirect edge is not client-setuppable, \sys excludes that edge from further path search and tries another candidate.
Only when $\varphi_\pi$ is satisfiable \emph{and} every indirect edge is client-setuppable does \sys emit $(\pi,\varphi_\pi)$.

The emitted pair is still a static (may) result: it shows a client-callable entry, jointly consistent entry conditions, and setuppable indirect calls---not that executing the path with some input reaches $s$.
These pairs are passed to P2, which builds a harness that establishes the required state, and to P3, which searches for triggering inputs.
