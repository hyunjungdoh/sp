\section{Design of \sys}
\label{sec:design}

\subsection{Overview}
\label{subsec:design-overview}

\autoref{fig:overview} illustrates the workflow of \sys.
As formalized in \autoref{sec:moti}, our goal is to determine whether a vulnerability in an upstream library~$U$ can be triggered through a downstream application~$D$.
This requires finding a path from a public API of~$D$ to the vulnerable operation~$s$, establishing the runtime state needed to execute that path, and finding input data~$X$ that triggers~$s$ under that state.

\sys addresses these requirements in three phases.
P1 recovers trigger paths and identifies the public APIs that establish the memory values required along each path.
P2 uses this information to synthesize a client harness, supplementing it with constants and configuration settings that can affect path execution but are not captured by P1.
P3 performs concolic execution on the generated harness to find input data that triggers~$s$.

The three phases address different obstacles to reaching~$s$.
A trigger path specifies the conditions for reaching~$s$, but does not tell a client how to establish them through~$D$.
P1 addresses this gap through \emph{setup attribution}, which connects path conditions to the public APIs that can establish the required state.
Even with these APIs, however, a path may not execute as intended: the harness must construct the required objects, select the appropriate indirect-call targets, and account for configuration settings that affect execution outside the entry arguments.
P2 addresses these issues through \emph{directed harness synthesis}, which turns the attributed context into an executable harness and guides exploration toward the recovered path.
P3 then searches for the input that triggers the vulnerability.

\PP{Design assumptions}
\sys analyzes the compiled intermediate representations of~$D$ and~$U$ with debug information, which provides function signatures, structure layouts, and field names.
It takes the location of~$s$ and the public APIs of~$D$ as input.
We assume that a client interacts with~$D$ only through these public APIs.
Values that cannot be established through them are treated as input-dependent and left to P3.

\subsection{Configuration Context Recovery (P1)}
\label{subsec:p1}

P1 recovers paths from~$D$ to~$s$ and determines how a client can establish the state required along each path.
It first constructs a call graph that captures direct and indirect calls across the two modules.
It then recovers trigger paths from suitable public entry points and attributes their required memory values to public setup APIs.

\subsubsection{Call graph and entry points}

A call graph built from direct calls alone misses paths that cross the boundary between~$D$ and~$U$ through indirect calls.
For example,~$D$ may register a callback that~$U$ invokes later, or either module may dispatch through a function pointer or virtual table.
To capture these paths, \sys performs a field-sensitive, flow-insensitive points-to analysis over both modules.
It connects function-pointer stores to indirect-call loads and resolves virtual calls through vtable entries.
Together with direct calls, these relations form a call graph spanning~$D$ and~$U$.

The starting points of a trigger path must be public APIs that a client can invoke.
Being public is not enough, because an API is callable only when a client can construct its arguments.
Scalars and byte sequences can be supplied directly, whereas handles, objects, and aggregates require a public producer.
A function that reaches~$s$ without such a producer is therefore not a starting point.
Its paths remain reachable, but only through its callers.
\sys ascends the call graph from such a function to the nearest callable public APIs.
These are the points at which a client first enters the path.

\subsubsection{Setup attribution}

For each entry point~$f_0$, \sys recovers trigger paths
$\pi=f_0\rightarrow\cdots\rightarrow f_n$ that reach~$s$.
A path alone, however, does not explain how a client can satisfy its conditions.
A condition may refer to a field of an object passed to~$f_0$, even though that field is written only by an earlier public API of~$D$.
Because a client cannot modify the internals of~$U$, it must establish the required value through the interface exposed by~$D$.
Thus, path recovery must also identify which public APIs can install the values required along the path.

Simply finding APIs that write to the same field is insufficient.
An API may write to a temporary object or to a different instance, or it may write a value that violates the path condition.
Calling such an API does not establish the state that the entry point will later read.
Setup attribution therefore has two tasks: express path conditions in terms of memory reachable from the entry arguments, and identify public APIs that can establish those conditions on the relevant objects.

\PP{S1: Express path conditions over entry-relative cells}
For a trigger path~$\pi$, \sys expresses each required memory location as a cell
$c=(o,\alpha)$, where~$o$ is an argument of~$f_0$ or an object obtained through a prior public call on those arguments, and~$\alpha$ is a constant field path within that object.
This representation identifies both the required value and the object on which a client must establish it.

\sys examines the branch predicates along~$\pi$ and retains those whose operands can be expressed as entry-relative cells and constants.
Predicates that depend on input data are left to P3.
When a caller branches on a callee's return value, \sys maps the return-value condition back to the values passed by the caller, allowing the requirement to be expressed in the same entry-relative form.
It also discards a path whose implied indirect-call targets contradict the call context.

The result is a set of conditions over cells reachable from the entry arguments.
This restriction identifies state that a client can establish through the objects it supplies to~$D$.
State outside this reach, such as fields of objects created internally by~$D$, is not attributed here and is handled during harness generation.

\PP{S2: Attribute required cells to setup APIs}
For each required cell~$c=(o,\alpha)$, \sys identifies public APIs that can establish its required value.
It first collects stores whose destination field matches the final field of~$\alpha$ by type and byte offset.
It then walks the call graph backward from these stores to the public APIs that reach them.

A matching store alone does not establish that an API is a valid setup operation.
\sys checks that the API operates on an object of the type that holds the required field, rather than writing a field with the same layout in an unrelated object.
It also examines the stored value against the required condition.
A constant that contradicts the condition rules the store out.
A value not fixed at analysis time is admitted, since a client may be able to supply one that satisfies the condition.
APIs that release the relevant object are excluded, since the entry point cannot subsequently read the required state from a destroyed object.

Among the admitted APIs, \sys retains those closest to the matching stores in the call graph.
This avoids selecting callers whose only role is to invoke another already identified setup API, while still allowing an API to qualify when its implementation forwards the operation to a private helper.
When multiple APIs can establish different required cells, \sys uses a greedy selection procedure that prefers APIs covering more uncovered cells, subject to a fixed limit.

The resulting configuration context records an entry point, its path conditions, and the setup APIs attributed to those conditions.
A context is retained only if every required cell has an attributed setup API or can be initialized directly, and the required return-value conditions are feasible.
\sys also drops a candidate API whose state on return would violate another required cell, so that the attributed APIs can be called together.
The retained contexts are passed to P2.

\PP{Precision of setup attribution}
Setup attribution requires more than matching field layouts.
The entry-relative representation restricts requirements to objects that a client can reach through the entry point, while the setup-API checks exclude operations that do not establish the required state on those objects or that write incompatible values.
This allows \sys to distinguish an API that configures the object later read by the entry point from a getter, a temporary-object builder, or an unrelated method that happens to write a field with the same layout.

Setup attribution is nevertheless an approximation, not a proof that the recovered path will execute.
The call graph and value information may over-approximate possible behavior, conditions are recovered per path, and the selected setup APIs form a bounded cover rather than an exhaustive set of ways to establish the state.
P2 therefore treats each retained context as a candidate harness configuration, and P3 determines whether an input can actually trigger~$s$.

\subsection{Harness Generation (P2)}
\label{subsec:p2}

P1 identifies the state required along a trigger path and the public APIs that can establish it.
P2 turns this information into an executable client harness.
Establishing the attributed cells, however, does not ensure that execution reaches~$s$.
Two decisions remain outside the conditions P1 recovers.
One is which registered implementation an indirect call selects at runtime.
The other is how configuration consulted inside~$U$ is set.
\sys therefore materializes the attributed context, and then supplies each of these decisions as an explicit choice.
These choices guide concolic exploration toward the recovered path without fixing every value in advance.

\PP{S1: Materialize the attributed context}
For each retained context, \sys generates a harness that interacts with~$D$ only through its public APIs.
It obtains the objects required by the entry point through public producers, reusing compatible objects when possible, and invokes the setup APIs attributed by P1.
For required cells that can be initialized directly, the harness writes the corresponding values before invoking the entry point, unless object construction or a setup call has already established them.
It then invokes the entry point with symbolic input.

The harness does not commit to every optional setup operation or argument.
Instead, it preserves the alternatives identified by P1 as choices for concolic exploration.
The initial execution follows the attributed context, while subsequent executions can explore other permitted choices.
Conditions that depend on input bytes remain symbolic and are handled by P3.

\PP{S2: Supply constants associated with registered targets}
A recovered indirect-call target does not by itself tell the harness how to select that target at runtime.
Libraries often choose a registered implementation using additional values stored alongside the function pointer, passed to its installer, or used by a factory that creates an object containing the pointer.
These values may not appear in any branch predicate, so P1 does not recover them as path conditions.
Without them, the harness may reach the dispatch point but select a different implementation.

For each indirect-call target~$t$ on a retained path, \sys therefore looks for constants associated with its registration.
It considers constants stored alongside the address of~$t$ in the registration call, passed alongside~$t$ to the function that installs it, or used by a factory that produces an object holding~$t$.
When a registration uses a constant table, \sys expands the table into its entries.

The harness offers these constants wherever it supplies a value that the library dispatches on.
In practice this is the name of the input, since a library commonly selects its implementation from the name of the data it is given.
An alternative carrying no such constant remains available.
Exploration is thus directed toward a recovered target without being confined to one dispatch choice.

\PP{S3: Prioritize configuration settings that affect the trigger path}
Even after the attributed cells are established, execution may leave the trigger path before reaching~$s$.
Some relevant fields belong to objects that~$D$ creates internally, while others are initialized from configuration defaults consulted inside~$U$.
Because these objects are not reachable from the entry arguments, P1 cannot attribute their fields to setup APIs.

The motivating example in \autoref{lst:moti_oiio} illustrates this case for the field in \autoref{lst:moti_vul}.
\texttt{RawInput} stores a LibRaw object in its member \texttt{m\_processor}.
Before calling \texttt{unpack()}, it reads
\texttt{config.get\_int\_attribute("raw:max\_raw\_memory\_mb", 2048)}
and writes the result to
\texttt{m\_processor->imgdata.rawparams.max\_raw\_memory\_mb}.
The client does not receive the LibRaw object directly.
Instead, it installs the named attribute on the \texttt{ImageSpec} passed to \texttt{open}.
Since this setting is outside the entry-relative cells recovered by P1, a harness that relies only on attributed setup calls may leave the default value~$2048$ in place and never reach the vulnerable operation.

To account for such settings, \sys traces the values that determine whether execution reaches~$s$ back to client-controlled sources.
The trace starts from branch conditions that govern progress along the trigger path and from the operands of~$s$.
It follows each value to its definitions and each field read to writes of the corresponding field, eventually identifying sources that a client can influence through public APIs of~$D$.
These sources commonly include named configuration lookups and the public setters that install their values.

The trace is restricted to functions reachable from the selected entry point.
It also preserves caller context when following shared helpers.
Without this, a common utility such as \texttt{std::min} would connect a value used near~$s$ to every unrelated caller of that utility.

Each configuration setting identified by the trace becomes a choice in the harness.
Settings not reached by the trace are not prioritized initially.
When a lookup uses a default value~$d$, the harness explores both leaving the setting unset, thereby retaining~$d$, and explicitly invoking the setter with a non-default value.
In the motivating example, the trace identifies \texttt{raw:max\_raw\_memory\_mb}, so the harness offers an explicit non-default limit before exploring unrelated attributes.
These settings are exploration preferences rather than constraints: they guide the search toward the trigger path, while P3 determines whether the resulting execution satisfies the required conditions.

For each retained context, \sys emits the harness together with the indirect-call targets P1 resolved at each site.
It also marks each function on the recovered path with its position along that path.
P3 uses this to resolve indirect calls during execution and to prioritize states that remain on the path.

\subsection{Concolic Execution (P3)}
\label{subsec:p3}

In P3, \sys performs concolic execution on each generated harness to find input data~$X$ that triggers~$s$ under the configuration~$C$ the harness establishes, completing~$\operatorname{Trigger}(U,X,C)$.
