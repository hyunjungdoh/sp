
\section{Design of \sys}

We present the design of \sys, which assesses the exploitability of propagated vulnerabilities by recovering the required downstream configuration context and identifying inputs that trigger vulnerabilities under that context.

Before describing the analysis procedure, we define its inputs and vulnerability target.

\subsection{Configuration Context Recovery (P1)}\label{subsec:p1}
P1 recovers the configuration context required to trigger an upstream vulnerability through a downstream application. \sys first constructs a cross-boundary call graph and identifies trigger paths from downstream public APIs to the vulnerable operation. It then analyzes the conditions along these paths and identifies the public APIs that can establish the required memory state.

\subsubsection{Call Graph and Entry Points}
Constructing a cross-boundary call graph requires resolving indirect calls through function pointers and virtual dispatch. For example, a downstream application may register a callback that the upstream component invokes later. 

To resolve indirect calls across both components, \sys performs a field-sensitive, flow-insensitive points-to analysis. The resulting call graph is represented as $G=(F,E)$, where $F$ denotes functions in both components and $E$ denotes their calling relationships.


%To resolve these calls, \sys performs a field-sensitive, flow-insensitive points-to analysis over both components. \sys connects function-pointer stores to indirect-call loads and resolves virtual calls through vtable entries. Together with direct calls, these relations form a call graph $G=(F,E)$, where $F$ represents functions in both components and $E$ represents their calling relationships.

Specifically, \sys constructs the call graph by adding three types of edges to $E$. \circled{1} For direct calls, it connects each caller to its explicitly named callee. \circled{2} For indirect calls, it uses points-to analysis to identify possible callees from function-pointer assignments and loads. For example, if a function pointer \texttt{ptr->field} stores the address of $f$ and an indirect call later loads this field, \sys adds an edge from the caller to $f$. \circled{3} For virtual calls, it resolves possible targets through \texttt{vtable} entries, including overriding methods in derived classes.

Given the constructed call graph, \sys selects public APIs as starting points for trigger paths. Let $I$ denote the public APIs of $D$, and let $R(f_v)=\{v \mid v \leadsto f_v\}$ denote the functions that can reach the vulnerable function $f_v$. \sys first retains APIs whose arguments a client can construct. Scalars and byte sequences can typically be supplied directly, whereas handles and objects may require initialization through public APIs. Let $I^\star \subseteq I$ denote this constructible subset.

To avoid redundant entry points, \sys excludes an API directly called by another reachable public API. The selected entry points are defined as follows:

\vspace{-0.7em}
\small{
\[
B_{\mathrm{entry}} =
\{f \in I^\star \cap R(f_v)
\mid \nexists c \in I \cap R(f_v):
c\neq f \land (c,f)\in E\}.
\]}

Here, $B_{\mathrm{entry}}$ contains constructible public APIs that can reach $f_v$ but are not directly called by another reachable public API $c$, where $(c,f)\in E$ represents a direct call from $c$ to $f$.

\subsubsection{Setup Attribution}
For each entry point $f_0 \in B_{\mathrm{entry}}$, \sys recovers trigger paths $\pi=f_0\rightarrow\cdots\rightarrow f_v$ leading to the vulnerable function $f_v$. 

Executing these paths may require specific values in object fields initialized through earlier downstream API calls. Therefore, \sys identifies the required memory values along each path and the public APIs that can establish them.

An API may write to the same field in a different object or assign a value that violates the path condition.

\PP{Setup API identification}
For each entry-relative cell $c=(o,\alpha)$ identified in the previous step, \sys identifies public APIs that can establish its required value. It first locates \texttt{store} instructions targeting fields that match the final field of $\alpha$ in type and byte offset. Let $W(c)$ denote the set of functions containing these \texttt{store}s. \sys then traverses the call graph backward from $W(c)$ to identify public APIs that can reach these functions.

However, a matching \texttt{store} does not necessarily indicate a valid setup API. Therefore, \sys checks three requirements: \circled{1} the API modifies the object associated with the required cell, \circled{2} the stored value can satisfy the recovered path condition, and \circled{3} the API does not release the required object. For the second requirement, caller-controlled values are considered configurable, while constants violating the condition are rejected.

The recovered configuration context consists of an entry point, its path conditions, and the setup APIs identified for the required cells. \sys retains a context only if each required cell can be initialized directly or through an identified setup API, and the required return-value conditions are feasible. It also excludes contexts with conflicting setup operations that cannot establish the required cell values. The retained contexts are passed to P2 for harness generation.

\PP{Precision of setup attribution}
The recovered configuration contexts are candidates rather than guarantees of executable trigger paths. The call graph and value analysis may over-approximate feasible behavior, and the selected setup APIs represent a bounded set of configuration alternatives. Therefore, P2 uses these contexts to generate executable harnesses, while P3 determines whether the upstream PoC input actually triggers the vulnerability under the established configuration.
