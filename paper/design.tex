\section{Design of \sys}
\label{sec:design}

\sys assesses whether a vulnerability in an upstream library can be triggered through a downstream application.
To do so, it recovers how a client can reach the vulnerable code and establish the required runtime state, and then searches for input data that triggers the vulnerability.

\PP{Overview}
\autoref{fig:overview} shows the workflow of \sys, which consists of three phases.
P1 recovers trigger paths from a public API of the downstream application $D$ to the vulnerable code in the upstream library $U$, together with the conditions required to execute each path.
P2 generates a client harness that follows a recovered path and establishes the required state through the public API of $D$.
P3 performs concolic execution on the harness to find input data that triggers the vulnerability.

\subsection{Recovering Trigger Paths (P1)}
\label{subsec:p1}

In P1, \sys recovers call paths from a public API of $D$ to the vulnerable sink $s$ in $U$, along with the conditions required to execute each path. 
The key idea is to extend the call graph across the $D$--$U$ boundary and express the conditions along a path in terms of the state available at its entry point.
This allows \sys to identify not only how a client can reach $s$, but also which conditions must hold along the way.

\PP{Cross-boundary Call Resolution}
A direct call explicitly identifies its callee, whereas an indirect call obtains its target from a function pointer stored in memory.
Such calls are common at the $D$--$U$ boundary: $D$ may register a callback in an object field, which $U$ later loads and invokes.
A conventional call graph misses this relationship because the registration and invocation occur at different call sites.

\sys resolves these calls through a field-sensitive, flow-insensitive points-to analysis on function pointers.
It represents a memory location as $\ell=(o,\alpha)$, where $o$ identifies an object and $\alpha$ denotes a field path within it.
The analysis propagates function addresses stored at these locations through stores, loads, and calls until reaching a fixed point.
At each indirect call, \sys adds edges to the type-compatible functions in the points-to set of the loaded location.
For virtual calls, it also adds edges to overriding methods in possible derived classes of the receiver. 
These edges extend the call graph $G=(V,E)$ with indirect calls across the $D$--$U$ boundary.

\PP{Entry-Point Identification}
The call graph may contain functions that reach $s$ but cannot be invoked directly by a client. 
\sys therefore selects entry points from the public interface of $D$.
It considers a function public if it is an exported shared-library symbol declared in the installed headers of $D$.
It further requires that the function's arguments be available to a client: scalar, byte, and string arguments can be supplied directly, while held arguments such as handles, objects, and aggregates require a public API that produces a value of the corresponding type.

Let $I$ denote the set of public APIs of $D$, and let $I^\star\subseteq I$ contain APIs whose arguments satisfy these requirements. 
Let
\[
R(s)=\{v\in V\mid v\leadsto_G s\}
\]
be the set of functions that can reach $s$. 
Among the APIs in $I^\star\cap R(s)$, \sys excludes an API if another public API in $R(s)$ directly calls it.
The resulting entry-point set is
\[
\begin{aligned}
B_{\mathrm{entry}} = \{\, f\in I^\star\cap R(s)\mid
&\nexists c\in I\cap R(s):\\
&c\neq f \land (c,f)\in E \,\}.
\end{aligned}
\]
\sys enumerates call paths from each selected entry point to the function containing $s$.

\PP{Path-Condition Recovery}
A call path alone does not capture the conditions that govern its execution.
These conditions may test fields of objects passed across function boundaries, so \sys represents memory accesses in terms of the entry-point arguments. 
Specifically, it models each access reachable from an entry argument as a \emph{cell} $c=(i,\alpha)$, where $i$ identifies the argument and $\alpha$ is a constant field path from that argument. 
When a callee accesses memory through one of its parameters, \sys maps the access to the corresponding cell at the entry point.
Predicates collected in different functions can thus be expressed over a common set of cells.

For each function along a trigger path, \sys examines intraprocedural paths from its entry to the next call site or the sink and collects their branch predicates.
It tracks whether each cell retains its entry value, has a known constant value, or contains a function-call result.
Predicates over known constants are evaluated directly; those involving entry-valued cells are propagated to the caller using the corresponding cells.
A predicate may relate a cell to a constant or to another cell.

A branch may also depend on the return value of a preceding call.
To recover the conditions behind such a check, \sys traces the check into the callee and collects predicates on its parameters along paths that return a value satisfying the check.
It then maps these predicates back through the call arguments. 
Finally, \sys uses an SMT solver to check the consistency of the recovered predicates and discards paths with contradictory conditions.

\PP{Indirect-Call Feasibility}
The points-to analysis identifies possible indirect-call targets, but a target must also be selectable by a client.
\sys checks whether each target can be determined by an entry argument, input parsed by $D$, or a preceding public API call.
In the last case, the API must establish the state that selects the target; in the first two cases, target selection depends on values supplied by the client.
Paths with targets that cannot be selected through these means are discarded.
The remaining paths and their recovered conditions are passed to P2.

\subsection{Recovering API Setup (P2)}
\label{subsec:p2}

In P2, \sys recovers the public API calls needed to establish the configuration context required by a trigger path.
The key idea is to trace each required cell to functions that write its value, and then trace those writers back to public APIs.
Since reaching a writer does not guarantee that its store executes, \sys further recovers the call sequence that reaches and performs the required write, including calls needed to construct its arguments.

\PP{Writer Identification}
Consider a required cell $c=(i,\alpha)$ recovered in P1. 
Its final field identifies the memory field whose value is constrained along the trigger path. 
\sys uses the type and constant offset of this field to identify candidate stores in $D$.
Let $\mathcal{W}(c)$ denote the functions containing stores with the same $(\mathrm{type},\mathrm{offset})$ pair as the final field of $\alpha$. 
It then traverses the call graph backward from these functions to find public APIs that can reach a candidate writer:
\[
\mathcal{A}(c)=
\{a\in I\mid
\exists w\in\mathcal{W}(c),\ a\leadsto_G w\},
\]
where $I$ is the set of public APIs of $D$.
These APIs are candidates for establishing $c$; \sys does not assume that reaching a writer necessarily executes the matching store.

\PP{API Sequence Recovery}
For each candidate API, \sys recovers a call sequence that executes a matching store with the required value. Constructing this sequence also requires resolving the API's arguments.
Scalar arguments can be supplied directly by the client, whereas held arguments must be obtained through public producer APIs.
Because a producer may itself require previously created objects or handles, \sys recursively follows these dependencies and places the required producer calls before the API that consumes their results.
The resulting sequence therefore includes both the call that performs the required store and the preceding calls needed to invoke it.

The source of a stored value determines whether it can be established during setup recovery.
A value may come from an entry argument, a preceding setup API, or input data parsed by $D$.
\sys recovers API calls for values supplied through entry arguments or established by setup APIs.
Values derived from input data remain unresolved for P3, which searches for data that supplies them while triggering the vulnerability.
The same distinction applies to indirect-call targets: \sys recovers calls that install a target, whereas targets selected by entry arguments or parsed input remain dependent on the corresponding client-supplied values.

\PP{Setup Consistency}
The sequences recovered for individual cells must be compatible when combined.
In particular, two sequences may write different values to the same cell. \sys checks value constraints on each shared cell and rejects a combination if the values conflict and neither sequence overwrites the field.
This check considers call order: a later write may establish the required value even if an earlier call writes a different one.

\sys applies this process to the cells required along a trigger path.
For each cell, its value must be supplied through an entry argument, established by a setup API, or determined by the data context.
A cell without any such source, or a combination of setup sequences with an unresolved value conflict, causes the candidate path to be rejected.
Otherwise, \sys combines the recovered calls and their producer dependencies into a setup sequence.
The generated harness executes this sequence before invoking the recovered entry API, establishing the configuration context under which P3 searches for triggering input data.


\subsection{Concolic Execution (P3)}
\label{subsec:p3}
