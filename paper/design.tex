\section{Design of \sys}
\label{sec:design}

In this section, we describe the design of \sys, which assesses vulnerability exploitability through downstream applications by recovering the calls and runtime state needed to trigger vulnerable behavior and finding inputs that trigger it.

\PP{Overview.}
\autoref{fig:overview} shows the workflow of \sys, which consists of three phases.
P1 recovers a trigger path, P2 generates a harness, and P3 performs concolic execution.

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{./design/overview_HJ_simple.pdf}
\caption{Overview of \sys.}
\label{fig:overview}
\end{figure}

In P1, \sys analyzes which call sequences from a public API of the downstream application can reach the vulnerable code in the upstream library, and which conditions those sequences require.
In P2, \sys builds a harness that invokes the recovered API sequence and establishes the runtime state those conditions demand.
In P3, \sys searches the harness for concrete inputs that trigger the vulnerability.


\subsection{Recovering Trigger Paths (P1)}
\label{subsec:p1}

The goal of P1 is to recover a \emph{trigger path}: a call sequence from a public interface of the downstream application $D$ to a vulnerable function containing the sink $s$ in the upstream library $U$, together with the conditions under which that sequence can execute.
Formally, P1 produces pairs $(\pi,\varphi_\pi)$, where $\pi=f_0\rightarrow\cdots\rightarrow f_n$ begins at a client-callable export of $D$ and ends at a function containing $s$, and $\varphi_\pi$ constrains the values and fields that make $\pi$ executable.
A client of $D$ never calls $U$ by name; it may invoke only $D$'s public interface.
Reaching $s$ therefore requires a walk that starts in that interface, proceeds through $D$, and crosses into $U$---often through an indirect call whose target was registered earlier by a store in $D$.
P1 recovers such walks in three linked steps.
It first resolves indirect calls so that cross-boundary edges appear in the call graph.
It then selects entry points at which a client may begin, rather than midpoints of $D$'s own call chains.
Finally, it checks whether each candidate sequence is jointly feasible under a single entry state.
The three steps serve one product: an executable, client-visible path to $s$ that later phases can turn into a harness and search for concrete inputs.

\PP{Resolving Cross-Boundary Indirect Calls.}
Direct calls name their callees and contribute a single edge to the call graph.
Indirect calls do not: the callee is a function pointer loaded from memory.
Across the $D$--$U$ boundary, $D$ often registers a callback by storing a function address into a field, and a later load---frequently in $U$---uses that address as the call target.
A graph that ignores these memory operations misses the crossing edge.
A graph that resolves every indirect call to all type-compatible functions invents edges to handlers that $D$ never registered.
P1 must therefore connect stores of function addresses to the loads that consume them, and emit call-graph edges only for those recovered targets.

P1 does this with a field-sensitive, flow-insensitive points-to analysis restricted to function pointers.
\autoref{fig:resolve-pta} summarizes the three operations.
\begin{enumerate}
\item \emph{Install.}
When the IR stores a value $v$ to an address $a$, P1 names the abstract location $\ell$ of $a$ and, if $v$ denotes a function constant $g$ (after stripping pointer casts and aliases), records $g\in\operatorname{Pt}(\ell)$.
Locations are field-sensitive: $\ell$ is a struct-field access path $(r,\mathit{off})$, or a non-escaping local/global cell when the address is used only for loads and stores at that object.
When optimized IR collapses field GEPs to byte offsets, P1 recovers the field path from TBAA metadata on the access so that distinct callback slots are not merged.

\item \emph{Propagate.}
Loads, pointer copies, casts, $\phi$/select merges, argument and return binding, and whole-object copies move tokens between nodes.
If a pointer value held at $u$ may flow to $v$, then $\operatorname{Pt}(u)\subseteq\operatorname{Pt}(v)$.
Propagation is flow-insensitive: the analysis closes these inclusions to a fixpoint without modeling store order.
Store and load cells whose field paths are suffixes of each other are linked, so a write through an outer path and a read through an inner path (or vice versa) share tokens.

\item \emph{Resolve.}
At an ordinary indirect call that loads its callee from $\ell$, every type-compatible function $g\in\operatorname{Pt}(\ell)$ becomes a call-graph edge from the caller to $g$.
An empty points-to set yields no edge.
Virtual calls are resolved separately: their targets are matching vtable methods of classes derived from the receiver's static type, not the points-to closure of a data field.
\end{enumerate}

The resulting call graph $G=(V,E)$ contains the cross-boundary edges that a store-to-load link can justify.
Without those edges, no path from $D$'s interface to $s$ would be visible; with them, the remaining steps can ask where such a path should start and whether it can execute.

\PP{Identifying Entry Points.}
Edges in $G$ identify functions that can reach $s$, but reachability alone does not identify where a client of $D$ may begin.
Let $I$ be the public interface of $D$---symbols that $D$ exports and declares in its headers---and let $R(s)=\{v\in V\mid v\leadsto s\}$ be the sink-reaching subgraph.
Every start must lie in $I\cap R(s)$.
That filter is not enough.
An export $f\in I\cap R(s)$ may reach $s$ only because another function $c\in R(s)$ already calls $f$: $f$ sits in the middle of a sink-reaching call chain.
Starting a candidate path at $f$ would ask the client to enter $D$ mid-sequence, skipping the setup that $c$ performs and producing a path no real client begins.

P1 therefore keeps only roots of the sink-reaching subgraph among public functions:
\[
B_{\mathrm{entry}} =
\left\{
f\in I\cap R(s)
\;\middle|\;
\nexists c\in R(s):(c\rightarrow f)\in E
\right\}.
\]
The side condition $\nexists c\in R(s):(c\rightarrow f)\in E$ excludes midpoints, not merely private callees: a public function called from another sink-reaching function is dropped even though it belongs to $I$.
Each $f_0\in B_{\mathrm{entry}}$ is client-callable, can reach $s$, and is not preceded on any sink-reaching path by another function in $R(s)$.
Every retained path will begin at such an $f_0$.

\PP{Checking Path Feasibility.}
A named sequence of call-graph edges is not yet an executable walk.
Inside each function, branches may divert control away from the next call in the sequence.
At each indirect step, the loaded location must hold the designated callee; otherwise the path's dispatch is unrealizable.
These requirements interact across the sequence: a branch condition in a callee may constrain an argument or field established only at the entry, and an indirect target may depend on the same state.
P1 therefore enumerates simple paths from each $f_0\in B_{\mathrm{entry}}$ to a function containing $s$, preferring fewer indirect edges and then shorter length, and checks each candidate for joint feasibility.

For a candidate $\pi=f_0\rightarrow\cdots\rightarrow f_n$, P1 builds a path condition
\[
\varphi_\pi =
\varphi_{\mathrm{control}}\land
\varphi_{\mathrm{dispatch}}
\]
as follows.
\begin{enumerate}
\item \emph{Intraprocedural routes, collected backward.}
Working from the sink toward the entry, P1 fixes, in each $f_i$, an intraprocedural route that reaches the call (or the sink) required by the suffix $f_i\rightarrow\cdots\rightarrow f_n$.
Starting from the sink ensures that each function's route is chosen under the obligations of later steps, rather than committing to a local path that later steps cannot continue.
Along each such route, branch decisions become atoms of $\varphi_{\mathrm{control}}$: the predicates that the route's taken edges demand.

\item \emph{Caller--callee linking.}
Across each edge $f_i\rightarrow f_{i+1}$, P1 connects the call's actual arguments to $f_{i+1}$'s formals and tracks how pointer arguments name entry-rooted cells (argument index and field suffix).
Conditions collected inside $f_{i+1}$ are thereby expressed, when possible, over the same cells visible at earlier frames, and ultimately over the state of $f_0$.

\item \emph{Dispatch constraints.}
When $f_i\rightarrow f_{i+1}$ is indirect, $\varphi_{\mathrm{dispatch}}$ requires that the location loaded as the callee hold $f_{i+1}$---the same field cells the points-to analysis named when resolving that edge.
Direct edges contribute no dispatch atom.

\item \emph{Projection and satisfiability.}
The combined condition may mention cells deep in the sequence.
P1 projects it onto values and fields available at the entry $f_0$: only those cells can be part of the client's initial state.
It then checks whether the projected constraints are jointly satisfiable under P1's may-layer solver.
Satisfiable paths are retained as trigger paths $(\pi,\varphi_\pi)$; unsatisfiable ones are discarded.
\end{enumerate}
A retained pair is a may witness that the call sequence and its conditions are consistent at a client-visible entry.
It does not yet install that state or supply a data input.
P2 turns $(\pi,\varphi_\pi)$ into a downstream harness; P3 searches under that harness for concrete inputs that trigger $s$.
