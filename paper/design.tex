\section{Design of \sys}
\label{sec:design}

\sys assesses whether a vulnerability in an upstream library can be triggered through a downstream application. It recovers the configuration context required to reach and trigger the vulnerable code, generates a client harness that establishes this context, and searches for input data that triggers the vulnerability.

\PP{Overview}
\autoref{fig:overview} shows the three-phase workflow of \sys.

In P1, \sys recovers the configuration context. It identifies trigger paths from a public API of the downstream application $D$ to vulnerable code in the upstream library $U$, then determines the API calls needed to establish the required state.

In P2, \sys generates a client harness that executes the recovered API calls and invokes the selected entry point. In P3, \sys performs concolic execution on the generated harness to find input data that triggers the vulnerability.

\subsection{Configuration Context Recovery (P1)}
\label{subsec:p1}

Recovering a call path from a downstream application $D$ to a vulnerable operation in an upstream library $U$ is not sufficient to determine whether the vulnerability can be triggered. 
The path must be reachable through $D$'s public interface, and the values required along the path may need to be established through prior API calls.
\sys therefore recovers both trigger paths and the configuration context required to execute them.
It first resolves calls across the $D$--$U$ boundary and identifies suitable public entry points.
It then extracts the conditions required along each path and traces the required values to the public APIs that can establish them.

\PP{Resolving Cross-Boundary Indirect Calls}
A conventional call graph misses calls made through function pointers, including callbacks that $D$ registers and $U$ invokes later.
To recover these paths, \sys connects function-pointer stores in $D$ to loads at indirect-call sites in $U$.
It performs field-sensitive, flow-insensitive points-to analysis to resolve possible targets, tracking function pointers stored in structure fields and handling virtual calls through vtable entries.
Direct calls contribute edges to the same graph, yielding a call graph $G=(F,E)$ over functions defined in both $D$ and $U$.

\PP{Identifying Entry Points}
Although $G$ identifies functions that can reach the vulnerable sink $s$, a client can invoke only public APIs of $D$.
Moreover, an API directly called by another reachable public API need not be selected as a separate entry point.
Let $I$ be the set of public APIs and $R(s)=\{v\mid v\leadsto_G s\}$ the functions that can reach $s$.
\sys first retains APIs whose arguments can be constructed through the public interface: handles, objects, and aggregates require a public producer API, whereas scalar, byte, and text arguments can be supplied directly.
Let $I^\star$ denote this subset. The entry points are then
\[
\begin{aligned}
B_{\mathrm{entry}} = \{f\in I^\star\cap R(s)\mid\;&
\nexists c\in I\cap R(s):\\
&c\neq f\land(c,f)\in E\}.
\end{aligned}
\]
This selection retains reachable public APIs that can serve as client entry points while avoiding redundant entries for APIs directly invoked by another reachable public API.

\PP{Recovering Path Conditions}
For each selected entry point, \sys recovers trigger paths $\pi=f_0\rightarrow\cdots\rightarrow f_n$ to $s$ and the conditions collected along each path, denoted by $\varphi_\pi$.
These conditions include relevant branch predicates and indirect-call targets. 
To express memory requirements in terms of values available to the client, \sys represents each memory cell reachable through an entry argument as $c=(i,\alpha)$, where $i$ identifies the entry argument and $\alpha$ is a sequence of constant field accesses identified by type and offset. 
Conditions on such fields can therefore be expressed as constraints on the corresponding entry-argument cells.

\sys collects conditions on these cells along each selected path. Conditions that can be expressed in terms of entry-argument cells are retained in $\varphi_\pi$, while conditions dependent on input data are left to concolic execution.
The retained cells include not only fields of public entry arguments, but also fields inside library-held objects that the path reads before it first crosses into $U$: without those values the entry never reaches the crossing.
When an open or similar call uses a field as the input file path, that cell is recorded as naming the input file rather than as a numeric constraint; the obligation is structural (the field must hold the file name) rather than a particular constant.
When a callee returns a value that its caller subsequently checks, \sys traces the caller's comparison back to predicates on the callee's parameters along paths returning a satisfying value, and maps these predicates through the call arguments.
This recovers requirements on values passed into the callee without treating its internal side effects as requirements on the caller's state.
The resulting $\varphi_\pi$ captures the conditions recovered for the selected path, rather than a complete characterization of all feasible executions.

\PP{Indirect-Call Feasibility}
Points-to analysis may introduce indirect-call targets that are possible in the linked program but incompatible with a particular entry-point path.
\sys checks the feasibility of recovered targets against the call context before retaining the corresponding path.
This avoids accepting a trigger path solely because its indirect-call target appears among the possible points-to targets.

\PP{Recovering API Setup Sequences}
The conditions in $\varphi_\pi$ describe values required along a trigger path, but they do not identify how a client can establish those values.
\sys therefore traces each required cell to its possible writers among prior public API calls.
For a cell $c=(i,\alpha)$, it identifies candidate stores by matching the type and offset of the final field in $\alpha$. 
Let $\mathcal{W}(c)$ denote the functions containing matching stores. 
\sys walks backward through $G$ from these functions to identify public APIs that can reach a matching store:
\[
\mathcal{A}(c)=
\{a\in\mathcal{I}_D\mid
\exists w\in\mathcal{W}(c),\ a\leadsto_G w\},
\]
where $\mathcal{I}_D$ is the set of public APIs in $D$. This identifies APIs that may establish the required field.
However, reaching a function containing a matching store does not guarantee that the store executes.
\sys therefore analyzes the relevant control flow and recovers a call sequence that reaches a store assigning a value compatible with the required condition.

When multiple APIs can write the same cell, \sys drops a lower-level interface only when a callable public API that takes the same held object already reaches a matching store; an interface that builds a fresh object of the field's own type does not set the embedded cell and does not cut the search.
For cells that must be set before the entry reads them (including fields inside held objects and cells on the $D$--$U$ boundary), a candidate is kept only when a text or byte argument of the API can flow into that field, or---for a cell that names the input file---when the API takes a name argument that the harness can supply as the input path.
\sys then selects writers across required cells using a greedy maximum-coverage strategy: at each step, it chooses the writer covering the largest number of uncovered cells, up to a fixed number of writer slots.
The resulting set is a bounded cover, rather than an exact minimum set.

\PP{Setup Consistency}
The recovered setup sequences must not contradict the conditions required along the trigger path. 
\sys compares value constraints imposed on the same cell and rejects a combination only when the constraints conflict and neither sequence overwrites the field.
This check detects incompatible value requirements without requiring a full satisfiability analysis of the setup and trigger paths. 
A configuration context is retained only when every required cell has a candidate way to obtain its value and the recovered return-value conditions are feasible.
For return-value conditions, \sys checks whether the corresponding callee can produce a value satisfying the caller's comparison, considering constants, null values, delegated returns, and reachable return paths. 
These checks determine whether the context can be represented through the available interfaces; they do not introduce return-value setters. 
Which candidate is used for each cell---and how the harness encodes it---is decided in P2.
The retained entry points, path conditions, and setup sequences are passed to P2.


\subsection{Harness Generation (P2)}
\label{subsec:p2}

The trigger contexts recovered by P1 describe the entry points, required values, and candidate setup APIs.
P2 turns each context into an executable harness that establishes that state through public APIs of $D$, while leaving alternative calls and values as symbolic choices for concolic execution.
It also analyzes dependencies leading to the sink to prioritize configuration choices that may affect its execution.

\PP{Choosing How to Establish Each Requirement}
For each required cell, \sys picks the first applicable way a client can establish it, then encodes that choice in the harness.
If the field lies in a public object the client builds and passes to the entry, the harness writes the required value before the call.
Otherwise, if a producer of a held object takes an integer argument that flows into the field, the harness chooses that argument from the admitted values.
Otherwise, if a public setter keyed by a tag or configuration name covers the field, or a prior public API writes it (subject to the P1 filters), the harness may invoke that call before the entry---or skip it, so that concolic execution can try both.
If a producer or prior call already leaves a compatible constant on every return path, no extra call is added.
If the entry itself fills the field while reading input bytes, the harness supplies symbolic input and leaves the value to P3.
A cell that names the input file is treated differently: the harness must pass the file name into a setup API (or into an ownable public field), rather than waiting for input bytes to invent the name; otherwise the entry never opens the file.
If none of these options applies, the context is discarded.
Conditions on input bytes themselves remain the responsibility of P3.

\PP{Constructing Harnesses}
Given those choices, \sys emits a harness that constructs required objects through public APIs of $D$, performs the selected setup calls, and invokes the entry with symbolic input.
When an argument requires an object, it selects a public producer of that type, recursively builds its arguments, and reuses objects of the same type when possible.
Producer choices are ordered by whether they take the input, construction cost, remaining free arguments, and API name, guiding the initial run without excluding other producers.

\PP{Representing Alternative API Calls}
A fixed setup sequence would cover only one way of establishing a context.
Optional setup and setter calls are therefore symbolic choices: invoke or skip.
The initial schedule follows the recovered context; later flips let concolic execution try other combinations.
The same mechanism covers tag-based and name-based setters.

\PP{Tracing Sink Dependencies}
P1 recovers conditions on fields reachable from entry arguments, but some conditions that affect the sink may involve internal objects or values computed during execution.
To identify these dependencies, \sys analyzes the function containing the sink.
It identifies branches that control whether the sink executes and traces the values used by those branches, as well as the operands of the sink, back to their sources.
The analysis follows SSA definitions, field loads and their corresponding stores, function arguments and return values across calls, and the incoming values and selecting branches of $\phi$-nodes.
It also examines arguments that determine allocation sizes. The trace stops at sources such as input reads, configuration values obtained by name, entry arguments, globals, and external calls.

\PP{Prioritizing Configuration Setters}
The dependencies recovered by this analysis do not add new constraints to the trigger contexts.
Instead, \sys uses them to prioritize configuration values and setters that may affect the sink during concolic execution.
For a name-based configuration read with default value $d$, for example, \sys makes the corresponding setter write a value different from $d$ when that setter is selected.
Skipping the setter therefore preserves the default, while invoking it explores a non-default value.
Other setters retain the default choice of skipping the call.
Branch conditions along the sink path remain the responsibility of P3's concolic search.

\PP{Filtering and Harness Output}
Finally, \sys discards contexts that cannot be realized through the available public interfaces or whose required return-value conditions are infeasible.
For each remaining context, it emits the harness together with the indirect-call target metadata recovered by P1.
P3 uses this metadata and call-graph distances to guide concolic execution toward the sink.
