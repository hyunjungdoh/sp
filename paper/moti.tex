\section{Motivation}\label{sec:moti}
% In this section, we formalize the problem addressed by \sys and illustrate why assessing exploitability through downstream applications requires recovering the calls and runtime state needed to trigger a vulnerable sink, as well as finding inputs that trigger it under that state.
In this section, we formalize the problem addressed by \sys and then illustrate the importance of \textit{downstream configuration context} through a motivating example.
We begin by distinguishing two complementary contexts that determine whether a propagated vulnerability is triggered through a downstream application:
\begin{itemize}
    \setlength\itemsep{0.0em}
    \item \textbf{Data context} is the input data delivered to the vulnerable upstream code.
    \item \textbf{Configuration context} is the downstream execution context that enables the input to trigger the vulnerability.
\end{itemize}
Therefore, a propagated vulnerability is exploitable through the downstream application only when both contexts satisfy its triggering conditions.

\subsection{Problem Statement}
\label{subsec:problem}
In this paper, we focus on recovering the configuration context required to trigger an upstream vulnerability through a downstream application.

Let \(U\) denote the vulnerable upstream component, \(D\) the downstream application, \(X\) the data context, and \(C\) the configuration context. 
Our goal is to recover a \(C\) under which the \(X\) triggers the vulnerability:
\[
\begin{aligned}
\operatorname{Exploit}(U,D)
\iff {} & \exists X \in \mathcal{X}_D,\;
           \exists C \in \mathcal{C}_D: \\
        & \operatorname{Trigger}(U,X,C).
\end{aligned}
\]
% In this paper, we investigate whether vulnerabilities in upstream libraries remain exploitable through downstream applications. Let $U$ denote an upstream library containing a vulnerable sink $s$, and let $D$ denote a downstream application that uses $U$. Triggering $s$ through $D$ requires both suitable input data and the runtime state in which $U$ processes that data. We distinguish two factors that affect whether $s$ is triggered:
% \begin{itemize}
%     \setlength\itemsep{0.2em}
%     \item \textbf{Explicit Inputs}: External data, such as input files or payloads, that reach $s$ and determine the data it processes.
%     \item \textbf{Implicit Inputs}: Runtime state established by $D$ that affects how $U$ processes the input.
% \end{itemize}

% An input that triggers $s$ in isolation may fail to trigger it through $D$ if the required runtime state is not established. Assessing exploitability therefore requires recovering how $D$ invokes $U$, including the calls, arguments, and runtime state involved in reaching the vulnerable sink. A harness can exercise this interaction, but constructing one requires recovering the call sequence and establishing the implicit inputs needed along that sequence. Even with these elements in place, the harness must still execute an explicit input that triggers $s$.

% \PP{Technical Challenges}
% Automatically triggering $s$ through $D$ involves three technical challenges. The first concerns recovering the call sequence needed to trigger the sink. The second concerns recovering the arguments and runtime state required along that sequence. The third concerns finding explicit inputs that trigger the sink when executed through the resulting harness.

% \PP{Challenge 1: Call Sequence Recovery}
% Triggering $s$ through $D$ requires recovering a sequence of calls that starts from $D$'s exported interface, crosses into $U$, and reaches the vulnerable sink. Merely finding some path that touches $s$ is insufficient: the recovered sequence must expose a way to establish the vulnerability's trigger condition. The challenge is to recover such a sequence across the $D$--$U$ boundary.

% \PP{Challenge 2: Argument and State Recovery}
% Recovering the call sequence does not determine whether the sequence triggers $s$. The calls must also supply the required arguments and establish the runtime state that governs how $U$ processes the input. The challenge is to determine which arguments and state the harness must provide or establish along the recovered sequence.

% \PP{Challenge 3: Sink Triggering through Execution}
% Even if the harness reproduces the required calls and establishes the necessary implicit inputs, the sink may not be triggered by an arbitrary input. The explicit input must drive execution through the $D$--$U$ path and satisfy the conditions required to reach the vulnerable operation under the state established by the harness. The challenge is to find explicit inputs that trigger $s$ through this execution.

\subsection{Motivating Examples}
\label{subsec:motivating}

To illustrate the importance of configuration context in assessing vulnerability exploitability, we use CVE-2026-24450 in \texttt{LibRaw} and its downstream client \texttt{OpenImageIO} (\texttt{OIIO}). The vulnerability affects \texttt{LibRaw} 0.21.1 and originates from an integer overflow in its floating-point DNG decoder.

As shown in \autoref{lst:moti_vul}, \texttt{LibRaw} computes the allocation size in 64-bit arithmetic (line \#3) and checks it against \texttt{max\_raw\_memory\_mb} (line \#4). If the check passes, the size is recomputed in \texttt{calloc()} (line \#6), where integer overflow can yield an undersized buffer. A pointer into this buffer is passed to \texttt{read()} (line \#10), reaching the faulting \texttt{memmove} (line \#14). \texttt{LibRaw} fixed the vulnerability in commit \texttt{a58727c} by reusing the previously computed 64-bit size for allocation.

In the downstream setting, however, the \texttt{OIIO} case shows that the presence of the vulnerable \texttt{LibRaw} code alone does not determine exploitability; the outcome depends on the configuration established by the downstream
application.

In \texttt{OIIO}, \texttt{raw:max\_raw\_memory\_mb} is a downstream configuration that controls \texttt{LibRaw}'s memory limit during decoding. This configuration takes effect when \texttt{OIIO} invokes \texttt{LibRaw::unpack()}, which eventually reaches the vulnerable DNG decoder shown in \autoref{lst:moti_vul}. Importantly, this downstream-provided value controls the allocation-size check that guards the vulnerable allocation: a large value allows the malicious input to pass the check and reach the vulnerable code, whereas a smaller value causes decoding to terminate earlier. Therefore, whether this configuration is applied before or after \texttt{unpack()} directly affects exploitability.

\vspace{5px}
\noindent\textbf{S1: Vulnerable but not exploitable.}
In \texttt{OIIO} v3.1.12.0, this downstream configuration was applied only after \texttt{unpack()}. Consequently, \texttt{LibRaw} decoded the same malicious input under its default 2,048 MB limit and rejected it before reaching the vulnerable allocation.

\vspace{5px}
\noindent\textbf{S2: Exploitable under a downstream configuration.}
Commit \texttt{f717fc7} moved the application of this configuration before \texttt{unpack()}, allowing the configured limit to affect decoding. With a value such as \texttt{raw:max\_raw\_memory\_mb=20000}, the same
input can pass the size check and proceed to the vulnerable allocation, ultimately reaching the faulting \texttt{memmove}.

\vspace{5px}
\noindent\textbf{S3: Exploitability removed by constraining the configuration.}
Following our report, commit \texttt{b112832} capped
\texttt{raw:max\_raw\_memory\_mb} at 16,383 MB before
\texttt{unpack()}. Under this cap, the same malicious input is again rejected before reaching the vulnerable allocation.

\vspace{6.3px}
Together, S1--S3 show that exploitability can change even when the upstream vulnerability and malicious input remain unchanged, solely because of the configuration established by the downstream application. Existing exploitability analyses do not adequately capture this configuration-dependent behavior and may therefore classify S2 as non-exploitable. We further examine this limitation of existing approaches in \autoref{sec:eval}.

Accurately assessing such cases requires identifying the downstream configuration that affects vulnerability triggering. However, this is challenging for two main reasons.

\PP{Challenge 1: Cross-boundary configuration context}
The configuration context spans downstream and upstream components: the downstream application invokes the upstream library through API calls, often via indirect calls. 
These calls make it difficult to recover the trigger call path across the boundary. 
However, recovering the call path alone is insufficient. 
The analysis must also recover the values and control-flow conditions that jointly determine whether the path is feasible across both modules~\cite{deng2025chainfuzz, li2025transferfuzz}.

\PP{Challenge 2: Execution feasibility}
% Even after the trigger path and its conditions are recovered, realizing them in an actual downstream execution remains challenging.
% The data context can affect downstream control flow and internal state before reaching the upstream sink, while the configuration context determines how the data reaches and is processed by the vulnerable code.
% Thus, the two contexts must be satisfied together in the same execution to trigger the vulnerability~\cite{cadar2008klee, ma2011directedse, luo2023selectfuzz}.

% In S1, the assignment follows \texttt{unpack()}, so decoding uses the default 2\,048\,MB limit. In S2, the assignment precedes \texttt{unpack()}, allowing a larger attribute value to take effect. In S3, the value is capped at 16\,383\,MB before decoding. Thus, the same call sequence can execute under different runtime states. We assume here that the harness has established S2's permissive limit.

% This example illustrates C3. Even with S2's call sequence and permissive limit, an arbitrary input does not trigger the vulnerability. The input-derived dimensions must satisfy two conditions: the byte size computed in the 64-bit check must remain within the configured limit, while the element-count product passed as the first argument to \texttt{calloc()} must overflow. The limit governs the first condition, whereas the input determines the dimensions and thus the arithmetic results. Because several input-derived fields jointly determine these values, a mutated input is unlikely to satisfy both conditions.
